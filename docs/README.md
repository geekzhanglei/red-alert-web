# Red Alert Web 文档导航

这里存放本项目的全部设计文档。项目是一步步从原型做大的，因此文档按「总体架构 → 分阶段子系统」组织，每一篇都明确写清两件事：

- **设计意图**：为什么这么做，做了哪些取舍，放弃了什么。
- **实现思路**：具体怎么做，包含数据结构、接口、伪代码和验收标准。

## 每篇文档的固定结构

为了让文档可以随项目一起长大，每篇阶段文档都遵循同一套模板：

| 章节 | 作用 |
| --- | --- |
| 目标 | 这个阶段要交付什么，一句话说清 |
| 验收标准 | 怎样算「做完了」，可勾选、可验证 |
| 设计意图 | 关键取舍和「为什么不」的理由 |
| 实现思路 | 数据结构、接口、算法、伪代码 |
| 与其他系统的关系 | 依赖谁、被谁依赖 |
| 风险与注意事项 | 提前避开的坑 |

## 核心原则速览

这些原则贯穿全部文档，是判断「某个决定对不对」的最终依据：

1. **逻辑与渲染分离**：游戏规则只操作纯数据 `GameState`，Phaser 只负责把它画出来。寻路、伤害、经济永远不能写在渲染回调里。
2. **固定 tick 驱动**：逻辑每秒跑固定 20~30 次，画面按显示器刷新率渲染。这是暂停、加速、存档、回放和未来联网的前提。
3. **数据驱动**：单位/建筑的数值在配置里，不在系统代码里。加一个新单位只改配置，不改逻辑。
4. **命令即历史**：玩家的每一次操作都编码成一条命令，游戏状态由「初始状态 + 命令序列」确定性地演化。存档和回放只是这条链的自然产物。
5. **网格坐标是唯一逻辑坐标**：寻路、碰撞、占用都在二维网格上做；屏幕像素和等距投影只在渲染层出现。

## 约定

- 单位、建筑、阵营一律使用原创名称（步兵、坦克、采矿车……），不引用商业游戏的名称、贴图、音乐或音效。
- 文档里的代码片段是 TypeScript，与 `src/` 保持一致（2 空格缩进、单引号、分号）。
- 每完成一个阶段，回头更新对应文档，把「实现中发现的问题」补进「风险与注意事项」。
