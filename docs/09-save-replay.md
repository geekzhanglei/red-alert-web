# 09 · 阶段八：存档、回放与优化

## 目标

实现存读档和战斗回放，并处理规模增长带来的性能问题。这一阶段是前七个阶段「确定性纪律」的集中兑现阶段。

## 验收标准

- [x] 游戏中可随时保存；重新打开后从启动菜单“继续战场”恢复到保存时的完整状态（含迷雾、生产队列、AI 状态）。
- [ ] 每局游戏自动记录命令日志；结束后可以回放整局，结果一致。
- [ ] 64×64 地图、双方各 50+ 单位时，逻辑 tick 稳定在 20/s，渲染不掉帧。

## 设计意图

**为什么回放 = 「初始种子 + 命令日志」，而不是每帧快照？**

如果每 tick 存一次全量状态，一局 10 分钟（12000 tick）就是 12000 份状态，体积爆炸。但回顾 [01 决策四](./01-architecture.md)：游戏是**确定性的**，状态由「初始状态 + 命令序列」唯一决定。所以回放只需存：

- 初始状态（地图种子、双方初始配置）
- 命令日志（`{ tick, playerId, command }` 的序列，通常每 tick 只有几条）

回放时重新喂一遍，结果必然一致——前提是前七阶段的确定性纪律没有破。**这个设计在阶段一就定了，现在只是收获。**

**为什么存档 = 「tick N 的全量快照 + N 之后的命令」？**

存读档要「从任意时刻继续玩」，不能从 0 重演（重演 40 分钟等不起）。所以存档是折中：保存时把当前 `GameState` 序列化成 JSON 落盘，之后的命令继续追加。读档 = 加载快照 + 继续演算。快照只在玩家点「保存」时产生一次，体积无所谓；命令日志照旧轻量。

**为什么要性能优化和回放一起做？**

性能优化（Web Worker、寻路批处理）不能破坏确定性。把回放当「回归测试」：任何优化上线后，跑一遍旧回放，结果一致才算数。两者绑定，优化才有安全网。

## 实现思路

### 1. 命令日志格式

```ts
export interface ReplayRecord {
  version: number;          // 格式版本，升级时做迁移
  seed: number;             // 地图与随机种子
  initial: { players: PlayerState[]; mapSeed: number };
  commands: { tick: number; playerId: number; command: GameCommand }[];
  endTick: number;          // 结束 tick
}
```

命令在「入队」时就带 tick 记录进日志（人类输入和 AI 命令一视同仁——AI 命令是确定性产生的，回放时由 AI 自己重发也可以，但**记录全部命令更稳**，避免 AI 实现改动导致旧回放失效；取舍：先记录全部命令）。

### 2. 存档快照

```ts
export function serializeState(state: GameState): string {
  // GameState 是纯数据 + Uint8Array 视野，全部可 JSON 化：
  // Uint8Array → number[]（或 base64），实体字典 → 数组
  return JSON.stringify(toPlain(state));
}
export function deserializeState(json: string): GameState {
  return fromPlain(JSON.parse(json));
}
```

如果 [01](./01-architecture.md) 的「GameState 不含 Phaser 对象」纪律守住了，序列化就是纯体力活；若里面混进了精灵引用，这一步就会逼你重构。**这是纪律回报最直观的地方。**

当前网页版把序列化结果包在带版本号和保存时间的本地存档信封中，写入浏览器 `localStorage`。局内选项提供“保存战场”和“读取存档”，启动菜单会显示最近一次存档的回合与时间，并允许继续或删除；读取会重新加载页面，再用快照创建 `Game`，因此不会复用旧场景的渲染对象。

### 3. 回放流程

```text
加载 ReplayRecord
  → 用 seed + initial 重建初始 GameState
  → 每 tick：把日志里 tick 匹配的命令注入命令队列，跑一次 game.update()
  → 渲染层照常画（可加 2x/4x 速度：一次 frame 推进多个 tick，见 01 的累加器设计）
  → 到 endTick 结束，可对比「终局状态哈希」校验一致性
```

### 4. 性能优化清单（按收益排序）

1. **渲染合批**：同贴图单位共用一个 Phaser 容器/图集，减少 draw call；地块先渲染成整张离屏 canvas，摄像机平移时不再逐块重画。
2. **寻路去重与缓存**：同编队单位共享一条路径；相同 (start,goal) 对缓存结果，地图占用变化时按区域失效。
3. **索敌空间索引**：战斗系统找「射程内敌人」从全实体 O(n²) 改成按格子桶（空间哈希）查邻格，n 大时收益显著。
4. **Web Worker 迁移**：把 `game.update()` 整块搬进 Worker，主线程只做渲染和输入。GameState 在 Worker 内演化，用 `postMessage` 把「本 tick 变更」或「全量状态（带结构共享）」发给渲染层。**放在最后做**，因为它是最大的结构性改动；前面几项优化通常已足够。
5. **视野更新脏矩形**：见 [08](./08-fog-minimap.md)，单位密集时再上。

优化必须遵守：**任何优化后，跑一遍已有回放，结果一致才算通过。**

## 与其他系统的关系

- 存档/回放是对 [01 确定性纪律](./01-architecture.md) 的验收；哪里坏了，说明哪里违反了纪律。
- 序列化覆盖 [06](./06-economy.md) 的生产队列、[07](./07-ai.md) 的 AI 状态、[08](./08-fog-minimap.md) 的视野数组——读档后这些都必须完好。
- 性能优化主要针对 [04 寻路](./04-selection-pathfinding.md) 和 [05 索敌](./05-combat.md)。

## 风险与注意事项

- **版本号必须写进存档/回放格式**。游戏改版后旧存档要能检测出来，报「存档版本过旧」而不是崩溃。
- 序列化要跑「保存 → 加载 → 逐字段对比」的单测，别相信肉眼。
- 确定性最大杀手是「某处漏用种子随机」和「遍历了对象键」。回放不一致时，先查这两个。
- Web Worker 是最后的手段：它把「状态在哪儿」的问题炸开，先确认前面几项优化不够再动它。
